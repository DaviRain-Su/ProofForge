# R5-010 — Add the first persistent bounded EVM storage vector

## Goal

Provide one reusable EVM SDK storage-vector component for UInt64 values — compile-time capacity,
explicit runtime length, checked active-prefix reads, and push/pop/set/clear mutation planning —
without adding a runtime slot allocator, a host pointer, a new top-level Ops/IR/Emit recipe, an
application special case, or an unbounded loop, and without hiding physical state writes from
applications.

## Delivered contract

`Evm.Sdk.StorageVec` binds the shared `Core.Value.BoundedVec` active-prefix semantics to the
existing EVM static-storage model:

- **Descriptor** (`Descriptor capacity`, `declare`, `Descriptor.wellFormed`): a compile-time
  `Storage.Static` bundle of the backing `Vector UInt64 capacity` field and the adjacent `UInt64`
  length scalar. `wellFormed` fails closed on zero capacity, non-UInt64/wrong-length backing or
  length payloads, and non-adjacent length slots. Handles are erased before extraction; no runtime
  layout object, slot allocator, or hashed namespace exists.
- **Runtime policy** (`wellFormed`/`isEmpty`/`isFull`/`canPush`/`canPop`/`active`/`canGet`/
  `canSet`/`canClear`/`popIndex`/`clearedLength`): pure `pf_inline` decisions over the explicit length
  scalar and a compile-time capacity literal. Every decision rechecks `length ≤ capacity`, so a
  malformed length fails closed on push/pop/set/clear rather than being silently repaired; full
  pushes, empty pops, and OOB get/set are separately rejected before any store, and the consumer
  picks the terminal (`CapExceeded()`, typed `malformed`/`oob`/`empty` errors, or a view fallback).

Because a generic helper returning an updated `Vector UInt64 capacity` is not an extractable
shape today, the component follows the `Roles.Set2` pattern: the SDK owns the reusable
length/index decisions, and every physical write stays a visible literal `State` field update in
the consumer (`entries.set … h`, `count := …`), with the compiler's `if h : … < capacity` guard
for the existing fixed-vector dynamic-index path. Its unreachable `else` maps to the consumer's
`malformed` terminal; no policy is re-derived or faked in the applications.

`clear`/pop intentionally leave stale backing slots unreachable (matching
`Core.Value.BoundedVec.clear` and the SVM account-vector pop contract); the Anvil matrices assert
the stale bytes directly. The documented resource shape is O(1) and capacity-independent per
operation — push: 1 distinct slot read + 2 stores; pop: 2 + 1; set: 1 + 1; checked read: 2 + 0;
clear: 1 + 1 — with the emitter currently re-loading the length slot per decision subexpression
(warm SLOADs) and owner gates adding their own Address-limb reads. No iteration exists anywhere.

## Consumers

- `Examples.EvmVecLog` — owner-gated bounded audit log, capacity 4: `record` (push, full →
  `CapExceeded()`), `amend` (set, OOB → typed `oob`), `wipe` (clear), `countOf`/`entryAt`
  (checked read with `0` fallback), `adminOf`.
- `Examples.EvmVecStack` — permissionless bounded LIFO, capacity 3: `push`, `pop` (empty → typed
  `empty`, popped value observable via `eth_call`), `clearAll`, `depthOf`/`topOf`; constructor
  seeds one genesis element.

Both declare their layout through `StorageVec.declare` in the exact `State` declaration order and
independently choose authorization and terminal policy. Neither stores a SDK object, Vector
handle, pointer, or runtime geometry.

## Compiler boundary

No Runtime/Ops/IR/Component/Emit case was added; the policy inlines to existing UInt64
comparisons and the existing fixed-vector dynamic-index load/store paths (`sload(add(...))` /
`sstore(add(...))` with the emitter's capacity re-check). One extraction-contract note: the
capacity argument of policy decisions must decode to a compile-time scalar literal (a consumer
`@[pf_inline] def capU64 : UInt64`), and the `Vector.set`/index hypotheses keep using the plain
literal capacity — the same contract `EvmStaticRoster` and `Lang` already follow. Non-UInt64
payloads, nested/wide elements, and runtime-computed capacities remain fail closed at the
descriptor/extraction boundary.

## Evidence

- `Tests.EvmStorageVecSpec`: policy truth tables including malformed lengths; descriptor pins and
  fail-closed variants (zero capacity, non-adjacent count, wrong payload leaf); consumer host
  behavior (push-to-full, LIFO order, stale-slot unreachability); extraction proofs that both
  consumers' slots and vector tables equal the declared layouts, plus emission guards for the
  dynamic-index load/store shapes.
- Canonical IR digests pinned in `Evm.Registry` (`EvmVecLog` `bea39a52948599c0`, `EvmVecStack`
  `8903e992dacdb808`); both compile with solc 0.8.34 (Cancun) at 2,492 B and 1,369 B deployed
  bytecode. All 26 registered EVM programs build; the whole Lean suite passes.
- `runtime-tests/evm/anvil_vec_log.sh` and `anvil_vec_stack.sh` cover constructor storage,
  ordered appends, full/OOB/unauthorized/empty atomic failures with exact revert selectors,
  pop return values via `eth_call`, clear, and post-clear stale-slot behavior. Both additionally
  inject an impossible over-capacity length through Anvil and prove push/pop/set/clear return the
  exact `malformed()` selector without repairing or otherwise writing storage; both are wired into
  the aggregate `anvil.sh` gate.

Remaining limits: single-limb UInt64 elements only; no enumeration/iteration API; `insert`/
`remove` in the middle are intentionally absent (not honestly supportable without an O(n) shift,
which the current no-unbounded-loop policy does not provide); descriptor `wellFormed` is a
host/test-side gate, with extraction-level layout equality proofs as the on-chain guard.
