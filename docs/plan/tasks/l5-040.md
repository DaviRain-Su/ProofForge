# L5-040 — Compose official Phoenix tag 4 withdrawal through reusable components

## Goal

Implement official Phoenix-v1 `ReduceOrder` without adding a Phoenix-specific top-level op, IR
node, or main emitter branch. Reuse the tag-5 account-resident transition and add only generally
reusable CPI/PDA shapes that the official Token withdrawal actually requires.

## Delivered

- Added raw tag 4 with the exact 26-byte reduce wire and nine physical accounts: current program,
  log PDA, writable market, readonly trader signer, trader base/quote accounts, base/quote vaults,
  and classic SPL Token program.
- Kept the official status distinction at the protocol boundary: tag 4 accepts reduce-allowed
  statuses 1..4; tag 5 and the shared storage reducer have no tag-4 status gate.
- Validated both trader token accounts and both vaults before mutation, including exact 165-byte
  layout, program owner, mint, trader/vault authority, header vault key, and executable classic
  Token program.
- Reused the same bounded `AccountStorage` Key4/FIFO lookup, one-based field mutation, and full
  RB removal/free-list transition as tag 5. Tag 4 claims exactly the lots unlocked by this call,
  preserving any pre-existing free balance.
- Added the generic classic Token tag-3 signed-transfer wrapper and `PdaSeed.accData`. The latter
  references a compile-time fixed, data-length-checked account byte slice of at most 32 bytes, so
  `["vault", market, mint, bump]` needs no copied mint buffer or heap allocation.
- Corrected generic effect sequencing: lexical account reads are materialized before later writes
  or CPIs, and ignored inline helpers retain their branch/effect continuation. Phoenix therefore
  persists sequence + 1 before log CPI while the audit header records the pre-increment snapshot.
- Matched exact audit behavior for both reduce tags: existing orders emit a 128-byte Header+Reduce
  batch; missing orders emit a 93-byte header-only batch. Tag 4 performs no Token CPI for zero
  release.

The stable layering remains:

```text
source semantics → Svm.EntryAdapter → Svm.AccountStorage → target-owned SVM backend/frame → sBPF
```

Persistent order/trader structures remain fixed-capacity account bytes with one-based indexes and
zero sentinels. No heap Map, detached node, copied tree, runtime geometry, or persistent pointer was
introduced.
