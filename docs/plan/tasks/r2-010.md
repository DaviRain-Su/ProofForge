# R2-010 — Checked fixed-account data resize

## Goal

Expose the useful contract of Solana `AccountInfo::resize` through a fixed typed account handle,
without pretending that account data is a general heap allocation or exposing Loader-v3 pointers
to source programs.

## Delivered contract

- `Account.Handle.resizeData newLength` erases the handle to a compiler-proven external account
  index. `Svm.AccountData.Call.resize` is one target-owned Component effect; it adds no top-level
  SVM Ops/IR/main-emitter constructor, System CPI recipe, application policy, persistent pointer,
  `Vec`, or `Map`.
- The target validates that the selected canonical header is not managed state account zero, is
  writable, is owned by the executing program, and has current/requested lengths at or below the
  10 MiB account ceiling. Current and requested growth over the invocation-entry length are both
  limited to Solana's 10,240-byte `MAX_PERMITTED_DATA_INCREASE`.
- The generic Component capability contract asks the Loader-v3 walk to retain immutable
  invocation-entry lengths in fixed scalar stack cells. This remains correct across sequential
  shrink/grow effects and canonical duplicate aliases without trusting an already-mutated current
  length or persisting runtime geometry.
- Shrink retains only the prefix. Grow zeroes `[current,new)` with `sol_memset_` before publishing
  the new u64 length, including shrink-then-grow in one invocation. Equal length is a validated
  no-op; every failed preflight exits `Custom(1)` before payload or length mutation.
- The API deliberately excludes managed-state resize, arbitrary account indexes, account close,
  rent top-up, System Allocate, native allocation, raw offsets, and source-visible pointers.

## Evidence

- `Examples.Svm.MemoryOps` independently consumes the SDK through `resizeData`, `shrinkThenGrow`, and
  `resizeThenFill`; target IR digest is `ce32c42ef22e10c6`.
- Focused Lean guards pin component-only lowering, one/two effect sequencing, alias/original-length
  walk capabilities, fixed account count, 10 MiB/10,240 bounds, zeroing, and current-length store.
- MemoryOps Mollusk passes 20/20. Five resize tests cover grow-prefix/zero extension, shrink,
  shrink→grow stale-byte clearing, post-resize checked memory access, exact +10,240 growth,
  +10,241 and >10 MiB atomic rejection, readonly/foreign-owner rejection, and managed-state alias
  rejection.
- Integration gates pass: Lean 382 jobs, Examples 260 jobs, SVM manifest 61 programs, locked
  Mollusk 404/404, EVM manifest 34 contracts, and Anvil 34/34. Surfpool 1.5.0 deployed and
  byte-verified the exact generic-emitter ELF for Phoenix (3,411,080 bytes / 3,371 Loader writes),
  PhoenixV1Profile (4,546,368 bytes / 4,493 writes), and RawEntry (46,336 bytes / 46 writes);
  no `solana-test-validator` was used.
