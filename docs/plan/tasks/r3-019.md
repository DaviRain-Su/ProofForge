# R3-019 — Share checked transient truncate

## Goal

Add Rust `Vec::truncate` parity to both invocation-local bounded containers without duplicating
target assembly or implying unbounded allocation, payload clearing, or reclaim on Solana's heap.

## Delivered contract

- `Svm.Sdk.Transient.Vector64.truncate` and `Svm.Sdk.Transient.Bytes.truncate` take one runtime
  `UInt64` length and remain behind their existing target-owned Component calls.
- Both first apply the shared active-marker and exact compile-time-capacity gate. If the requested
  length is smaller, only logical length changes. Equal or larger values, including `UInt64.max`,
  are successful no-ops.
- `Svm.Transient.Emit.emitTruncate` owns that transition for both concrete emitters. It uses an
  unsigned comparison without subtraction, so the no-op path cannot overflow.
- Truncation does not clear stale payload, allocate, free, reallocate, reclaim bump space, expose
  a native pointer, or add a top-level Ops/IR/main-emitter constructor.

## Evidence

- `Tests.SvmTransientVectorSpec` and `Tests.SvmTransientBytesSpec` pin canonical Component identity,
  source effect order, and the shared truncate assembly gate.
- `runtime-tests/solana/tests/memory_ops.rs` verifies shrink, equal-length no-op, and
  `UInt64.max` no-op for both containers under Mollusk; MemoryOps passed 15/15 tests.
- MemoryOps target IR digest: `96f938c65992b93a`.
- Emitted sBPF assembly: 145,351 bytes. Linked ELF: 48,448 bytes, SHA-256
  `a8e04951bd41070e604e8844a72e844d25137a1e35362282a1fdf5c34b23e150`.

Multiple simultaneous same-type handles, generic POD elements, bounded insert/remove-at, and
iteration remain separate resource contracts rather than implicit consequences of truncation.
