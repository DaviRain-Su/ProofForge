# R3-025 — Compose fixed-account close and refund

Date: 2026-08-30
Status: done

## Goal

Provide the common Solana program-account close pattern as one reusable high-level SDK operation,
without adding another Runtime leaf, protocol operation, IR variant, component, or emitter recipe.
The operation must use fixed account handles, preserve a pre-effect balance snapshot, and remain
atomic when its second checked effect fails after the account-data resize.

## Delivered contract

- `Account.Handle.closeTo destination` is an ordinary `@[pf_inline]` Lean composition. It snapshots
  the source balance exactly once, calls the existing zero-initializing `resizeData 0`, transfers
  that complete balance through the existing checked `transferLamports`, and returns the refund.
- Source and destination geometry remains compile-time fixed. The source must be an external,
  writable current-program-owned account. The destination must be writable and canonically
  distinct but may be foreign-owned. Managed-state source aliases, readonly/foreign sources,
  malformed account data, duplicate source/destination aliases, insufficient balance and
  destination overflow retain the underlying `Custom(1)` policy.
- The resize intentionally precedes the drain. Solana instruction rollback makes a later transfer
  failure atomic: current data length, payload and both balances are restored together.
- Draining to zero is the account lifecycle boundary. This helper does not add owner reassignment,
  rent top-up, System CPI, runtime-selected account indexes, persistent pointers, heap allocation,
  or a fake general allocator.
- `Examples.LamportTransfer.closeVault` is a non-Phoenix consumer. Application code sees only the
  typed SDK method; all Loader-v3 offsets and checks stay target-owned.

## Evidence

- Focused extraction guards pin one pre-effect lamport snapshot and exact
  `balance → resize → transfer → return` order. The transfer amount and public result reuse the
  same local, proving that the drained post-state balance is not reread.
- LamportTransfer Mollusk passes 15/15. The three close tests cover a nonempty program-owned source
  whose data becomes empty and full balance reaches a foreign-owned destination, plus destination
  overflow and same-canonical refund alias failures that restore the prior resize byte-for-byte.
- LamportTransfer digest is `795d11e30ee48fb5`; assembly is 31,362 bytes and linked ELF is 10,648
  bytes with SHA-256 `f091c930106769bd466adf1c28d5887a9ca3aef1fe67fcb718451c0d3934d926`.
- Surfpool 1.5.0 deployed that exact ELF through 11 normal Loader-v3 write transactions and the
  complete deployed ProgramData bytes matched the local artifact. No Test Validator or direct
  state-write deployment path was used.

## Boundary

This is fixed-handle program-account lifecycle composition, not arbitrary account destruction.
Rent top-up, close-authority policy, owner reassignment for a still-funded account,
runtime-selected remaining-account mutation, and AccountView/direct-mutation variable-walk
unification remain separate work. Token account close continues to use the typed Token CPI facade.
