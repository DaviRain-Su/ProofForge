# R5-008 — EVM checked allowance core

## Goal

Move owner/spender allowance mechanics out of application-shaped map expressions and into one
reusable explicit-handle SDK policy. Close UInt256 increase wraparound and checked delegated spend
without adding an ERC-20 or allowance recipe to Ops or Emit.

## Delivered contract

- `Evm.Sdk.Fungible.Allowances` is an explicit compile-time `Storage.AddressPairMap256` handle.
  It owns allowance lookup/set, next-value calculation, checked increase/decrease/spend gates and
  writes, and the existing typed `Insufficient(held,wanted)` terminal.
- Increase requires `next ≥ current`; decrease and spend require `current ≥ amount`. All methods are
  O(1), and mutation methods retain explicit preconditions so applications choose failure/event
  ordering.
- Token consumes the core for approve/increase/decrease/burnFrom/transferFrom. Pause and zero-address
  gates, permit authorization, and Approval/Transfer ordering stay visible in the application.
- Ownable is the second consumer. Its engineering allowance fixture intentionally widens UInt64 to
  UInt256 and replaces the old overwrite-shaped `spend` with checked subtraction and atomic
  insufficient failure.

There is no new Runtime leaf, Op/IR/Component/Emit case, selector/topic/error recipe, runtime layout
object, heap allocation, or cross-target storage abstraction.

## Resource and fail-closed boundary

The handle binds one persistent EVM pair-hashed namespace at compile time. The component does not
infer caller authorization, zero-address policy, permit ownership, infinite-allowance sentinels, or
event ordering. Those policies remain explicit in consumers. Calls that skip the documented
precondition are outside the SDK contract; both shipped consumers gate every decrease/spend.
