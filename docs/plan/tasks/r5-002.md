# R5-002 — Declare reusable EVM static storage layouts

## Goal

Give EVM contracts a reusable, target-owned way to bind static storage geometry once instead of
repeating slot numbers in application code or adding another protocol-shaped Emit recipe. The
surface must cover the fixed state shapes already supported by extraction, remain compile-time
metadata, coexist without drift with hashed-map namespaces, and fail closed on malformed
declarations.

This is the static-storage foundation of R5, not a runtime slot allocator and not completion of the
EVM SDK. Generic handle-driven field access would require a future shared Extract projection hook;
this slice does not fake that capability with hidden `sload`/`sstore` intrinsics.

## Delivered contract

`Evm.Sdk.Storage.Static` provides:

- `Leaf` descriptors for Bool/u8/u16/u32/u64, three-limb Address, and four-limb UInt256/Bytes32;
- `Spec` composition for leaves, flat records, fixed arrays, and fixed arrays of flat records;
- a consecutive `Layout` cursor and phantom-typed `Handle α` values with base slot, slot count,
  vector length/stride, field lookup, and wide-limb lookup;
- deterministic compatibility names matching extraction (`field_wN`, `record_field`,
  `array_N`, and `array_N_field`);
- whole-layout validation for supported widths, nonempty/unique flattened names, exact leaf count,
  and consecutive slots.

Declarations are ordinary immutable Lean values erased before extraction. Consumer methods keep
using ordinary typed State fields, so their established lowering remains
`Extract → EVM IR → direct sload/sstore`. `Tests.EvmStaticStorageSpec` compares the extracted State
slot schema with each declaration's derived leaf table; there is no second hand-written expected
slot list and no application name in Runtime/Component/Emit.

`Storage.Static.Layout` is intentionally distinct from the existing `Storage.Layout` hashed-map
namespace cursor. Static slot allocation therefore cannot move map bases or change
`keccak(key || base)` semantics.

## Consumers and evidence

- `EvmStaticCounter` declares a narrow scalar flag, UInt256, and flat record. Its constructor stores a
  narrow seed into the wide value and bakes an immutable owner; mutations exercise a wide update,
  one record field, neighboring-slot preservation, owner gates, and pause gates.
- `EvmStaticRoster` declares a stored Address, fixed three-element record vector, and Bool. Runtime
  indexing is bounded before the existing vector write; OOB, non-admin, and closed updates leave
  all slots unchanged.
- Both contracts are registry/aggregate examples. Their dedicated Anvil matrices inspect raw
  storage as well as typed getters, pinning the physical declaration contract independently of
  source-level host behavior.

Canonical EVM IR digests are `91b41fb32d550fd3` (`EvmStaticCounter`) and
`f1bf627143b860c3` (`EvmStaticRoster`). Deployment bytecode sizes are 2,367 B and 1,703 B.

## Resource and fail-closed boundary

- Descriptor construction is compile-time work; runtime storage and memory overhead is zero.
- Validation cost is compile-time and bounded by the finite declaration leaf table; deployed code
  carries no descriptor traversal.
- Empty top-level/flattened names, duplicate names, unsupported widths, arbitrary wide runs,
  malformed records, and nonconsecutive manual layouts fail validation.
- Recursive records, dynamic arrays, mappings through the static cursor, runtime-selected
  geometry, generic handle loads/stores, and packing multiple leaves into one EVM slot are not
  implied by this slice.
- The only runtime array index in the fixtures is checked against fixed capacity before storage
  mutation; there is no runtime allocator, pointer, or dynamic persistent collection.

## Verification

- Focused descriptor/extraction/build gate: 129 Lean jobs.
- Both registered contracts compile with solc 0.8.34; dedicated Anvil raw-slot/access/OOB matrices
  pass.
- `lake build Tests`: 264 jobs; aggregate Anvil: 20/20.
- Shell syntax, ownership, and whitespace gates cover the integrated files.
