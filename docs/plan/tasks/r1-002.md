# R1-002 — Shared allocation-free boundary values (source slice)

## Goal

Move logical `UInt128`, `UInt256`, and `FixedBytes n` values out of the EVM runtime and into the
shared source language without introducing dynamic allocation. Make Extract derive typed boundary
metadata and fixed scalar-limb return plans from those source types while keeping wire encoding and
persistent layout target-owned.

This is the **source-value slice** of R1-002. It does not claim that SVM Borsh or EVM aggregate ABI
binding is complete.

## Delivered

- `Core.Value.UInt128` and `Core.Value.UInt256` use two and four least-significant-first `UInt64`
  limbs respectively. `Core.Value.FixedBytes n` uses a fixed four-limb carrier and accepts only
  literal sizes `1 ≤ n ≤ 32`; no `Array`, `Map`, heap buffer, native pointer, or runtime-sized
  payload is part of these values.
- Extract derives `.uint128`, `.uint256`, and `.fixedBytes n` metadata and expands returns to exactly
  `2`, `4`, and `ceil(n / 8)` scalar limbs. Zero-length, over-32-byte, and nonliteral/polymorphic
  `FixedBytes` boundaries fail closed.
- Existing `Evm.Runtime.UInt256` and `Evm.Runtime.Bytes32` names are compatibility aliases to the
  shared values. Their constructors remain source-compatible, while EVM continues to own ABI word
  order, padding, calldata guards, and storage layout.
- Canonical projections now point at the shared structures. Extract still recognizes elaborated EVM
  alias names at the compatibility boundary because Lean may retain an abbreviation name in a
  declaration signature.

The ownership path is now:

```text
Core.Value logical fixed limbs
        │ Extract validates literal shape and derives Core.Codec metadata
        ▼
Core.Target typed method boundary
        ├── SVM adapter ──▶ exact-cursor Borsh plan (pending)
        └── EVM.Codec ───▶ ABI carrier/padding plan (pending for u128/FixedBytes n)
```

`FixedBytes n` carrier bits outside the first `n` logical bytes are not persistent data. Each target
adapter must reject or normalize noncanonical final-limb padding at its wire boundary; Core does not
encode SVM account geometry or EVM word alignment.

## Verification

- `Tests.CoreCodecSpec` covers all three shared values, exact return-limb plans, preserved EVM
  aliases, valid bounds, and fail-closed invalid/nonliteral `FixedBytes` declarations.
- `lake build Tests` passes 237 jobs and `lake build` passes 98 jobs.
- All 51 SVM programs and all 15 EVM programs build.
- The locked Mollusk suite passes 285/285 with one test thread.
- The EVM Anvil suite passes 15/15.
- Ownership and whitespace guards pass.

The current SVM examples do not expose these new boundary types, so this source-only slice does not
change their generated ELF. Surfpool 1.5.0 deployment is therefore not repeated; it remains the only
authorized local deployment gate when a later adapter slice changes a deployable SVM artifact.

## Next

Bind the values to both targets without moving physical layout into Core:

1. SVM derives exact-cursor, little-endian Borsh decode/return plans into fixed scalar locals.
2. EVM derives one-word `uint128` and left-aligned `bytesN` calldata/return plans, including canonical
   high-bit and low-byte padding checks.
3. One logical fixture exercises both bindings. Malformed padding, dynamic sizes, recursive shapes,
   and resource-budget overflow continue to fail closed before emission.
