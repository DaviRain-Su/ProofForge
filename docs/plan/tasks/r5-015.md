# R5-015 — EVM persistent bounded StorageBitmap

## Goal

Bind the shared bounded BitSet law to honest EVM persistent storage as a reusable SDK component,
without adding another Runtime/Ops/IR/Emit recipe or pretending that EVM mappings are enumerable.

## Delivered contract

- `Evm.Sdk.StorageBitmap.Descriptor bits` declares exactly one ordinary static
  `Vector UInt64 ((bits + 63) / 64)` field. Bit capacity and storage geometry are compile-time
  values; no runtime slot allocator, length header, host container, or pointer exists.
- `inRange` is the single bounds authority. `wordIndexOf`, `maskOf`, `containsOf`, `setOf`,
  `clearOf`, and `toggleOf` implement the same 64-bit packed-word arithmetic as
  `Core.Collections.BoundedBitSet`. An OOB index is rejected before word/mask use and cannot alias
  a lower bit.
- The SDK owns reusable decisions and bit arithmetic. Consumers retain explicit fixed-vector State
  reads/writes because the current extractor requires the vector field and bounds proof at the
  write site. Each operation touches one selected word, so the storage shape is O(1) and independent
  of capacity.
- EvmFeatureFlags combines owner-gated idempotent set/clear/toggle over 128 bits. EvmClaimBitmap
  independently provides permissionless one-time claims over 130 bits, including a partial final
  word. Neither consumer contains numeric storage slots or lower Emit/IR imports.

## Evidence

- `lake build ProofForge.Evm.Sdk Tests.EvmBitmapSpec` passes 165 jobs. The focused suite pins
  descriptor failures, shared BitSet agreement, 63/64 boundaries, partial final-word behavior,
  OOB no-aliasing, both consumer state transitions, extracted static slots/vector shapes, and
  emitted div/mod/shift/bitwise operations with no capacity loop.
- The normal solc 0.8.34 registry build produces all 30 contracts. EvmFeatureFlags digest is
  `5cc9bb266f23487f` with 2,662-byte deployment bytecode; EvmClaimBitmap digest is
  `d91809979ad94cdc` with 763-byte deployment bytecode.
- Dedicated Anvil matrices cover owner/replay policy, idempotence, 63/64 word boundaries, final
  in-range bits, OOB/huge-index failure without aliasing, and persistence across failed
  transactions. Both consumers run through the normal registry artifact path and aggregate Anvil
  gate (30/30); the 360-job aggregate Lean gate also passes. No worker-only assembly bridge remains.

## Explicit boundary and follow-up

This is a 64-bit-word bounded semantic analogue of OpenZeppelin BitMaps, not its exact 256-bit
mapping layout. Bulk clear, enumeration, counting, tracked-key sets, checkpoints, dynamic bit
capacity, runtime slot allocation, and hidden storage writes remain unavailable. They require
separate bounded policies and explicit O(n) resource contracts rather than a bitmap opcode.
