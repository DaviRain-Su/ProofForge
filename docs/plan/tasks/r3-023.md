# R3-023 — First-class allocation-free SVM Pubkey values

Date: 2026-08-30
Status: done

## Goal

Close the mainstream-parity "一等 32-byte address" gap for source/SDK code: applications should
name and compare complete 32-byte Solana public keys through a reusable typed `Pubkey` value
instead of repeating `keyWord 0..3` / `ownerWord 0..3` call sites. The slice must stay SDK/source
composition over the four existing UInt64 account key/owner projections — no new
Runtime/Ops/IR/Component/Emit operation, feature probe, emitter recipe, heap allocation, base58
decoder, pointer, or runtime account index.

## Delivered contract

- `Svm.Sdk.Pubkey` gains value-level composition: `Account.Handle.key` / `.owner` project the
  complete 32-byte key/owner of one statically selected account as a first-class `Pubkey`;
  `Pubkey.notEquals` is the complement of `Pubkey.equals`. `Account.Handle.sameKey` and
  `.ownerIsKeyOf` are now defined as value equality over those projections, so one primitive
  (`Pubkey.equals`) owns the canonical four-word comparison.
- `Pubkey.equals` is written over the `pf_inline` word projections rather than a
  two-discriminant `match`. Extraction deliberately does not iota-reduce multi-discriminant
  matchers, so the projection spelling is what keeps complete-key equality extractable; this
  boundary is now documented at the definition.
- Kernel-checked `pubkey_notEquals_iff` joins the existing reflexivity/symmetry proofs; all
  proofs rely only on standard axioms.
- `Examples.PubkeyGate` is an independent (non-Phoenix) consumer: fixed authority/owner keys, a
  runtime-supplied key built once from four scalar entry words, keys/owners projected from three
  statically selected accounts, and one shared `grants` policy consumed by seven views plus a
  gated mutation. No application site mentions word indexes or offsets.

A `Pubkey` value remains compiler data: it can be constructed from scalars, projected from fixed
accounts, passed between `pf_inline` helpers, and compared, but it never crosses an entry
boundary as an aggregate and never becomes a heap or account-resident object. Aggregate
entry-input binding of a four-limb record is unchanged R1 scope and was not needed here.

## Evidence

- Focused Lean gates (`Tests.SvmSdkPubkeySpec`): host erasure identities, literal word pinning,
  all-limb equality/inequality truth table, static handle bounds, zero ext-op payloads in every
  extracted method, exact `accKeyWord`/`accOwnerWord` leaves per view, four scalar parameters
  for the runtime-supplied key, static four-account prefix, and emitted-assembly guards for all
  four literal limbs, complete key (+8..+32) and owner (+40..+64) walks, executable-flag read,
  and the absence of allocation/CPI/crypto vocabulary.
- Canonical IR digest `8374e353a1923c12`; assembly 57,874 bytes; linked ELF 19,416 bytes; ELF
  SHA-256 `51ff1e0b4ad6c4f07af47f31bacd93b084b865a9e570f3ca7f4d49631ec8577a`.
- Mollusk 24/24: exact fixed-key match, mismatch in each of the four words (including outside
  word0), runtime-supplied key equal/mismatch, key-vs-key and owner-vs-key/owner-vs-constant
  matching, canonical executable+key+owner authentication, gated accept success with exact
  state update, unauthorized mismatch failing closed with byte-identical state, duplicate-alias
  equal-key positions failing closed, and truncated invocations failing closed.
- Aggregate qualification: all 61 registered SVM builds with unchanged digests for the 60
  pre-existing programs (TokenStateView/PhoenixV1Profile consume the recomposed APIs with no
  digest drift), artifact manifest/ownership/no-sorry gates clean.

## Boundary

Passing or returning a whole `Pubkey` as one entry argument/result needed the static aggregate
Borsh binding to treat compiler-owned SDK values as logical schema. That separate target-binding
work is now complete in [R3-024](r3-024.md); it does not change this slice's value-composition
contract. Equal keys across two
distinct account positions are Loader-v3 duplicate aliases and fail closed before method bodies;
complete-key equality is therefore observed on-chain as inequality or as key-vs-owner/constant
matches. Surfpool remains the sole deployment qualification environment; this slice adds no
deployment smoke and does not use Test Validator.
