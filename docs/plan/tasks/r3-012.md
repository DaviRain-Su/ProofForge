# R3-012 — Source-visible invocation-local `Vector64`

## Goal

Turn the transient SDK's descriptor-only fixed-vector plan into a usable bounded on-chain vector
without exposing a native address, pretending that Solana's bump allocator reclaims memory, or
adding another collection recipe to generic SVM Ops/IR/Emit.

## Delivered contract

- `Svm.Sdk.Transient.Vector64.bounded capacity` is compiler-erased geometry for one
  invocation-local `u64` vector. It exposes `begin`, `push`, `set`, `clear`, `finish`, `length`, and
  `get`; capacity is static while values and indexes remain ordinary runtime `UInt64`s.
- `Svm.TransientVec` owns the typed call/query vocabulary behind the existing Component bridge.
  Calls remain effects and queries remain values, so generic extraction, CFG, and target IR keep
  one component case rather than gaining vector operations.
- `Svm.Heap.Emit.emitAllocate` is the single official-shaped 32 KiB downward bump interpreter.
  BatchRecorder was migrated to it byte-for-byte, and Vector64 allocates exactly `capacity × 8`
  bytes with 8-byte alignment. A second allocation observes the first allocation's consumed heap.
- Exactly one Vector64 handle is active at a time in this slice. The target checks active state and
  static capacity before every mutation/query. `finish` clears scalar metadata but deliberately
  does not reclaim the allocation, matching Solana's no-op deallocation contract.
- Full capacity or runtime OOB terminates with `0x1202`; inactive or mismatched-capacity use with
  `0x1203`; allocator OOM with `0x1201`. No unchecked pointer or partial success reaches source or
  persistent state.

`Examples.MemoryOps` covers dynamic push/set/get, clear/length, full, OOB, capacity mismatch, and
an exact 32 KiB exhaustion path. `Examples.AccountView.stageSelected` independently stages a
runtime-selected account word through the same vector.

## Extraction and lifetime boundary

The source handle contains no pointer. Heap position and vector pointer/length/capacity/active
metadata exist only in target-owned invocation memory; all are discarded after the instruction.
Persistent vectors remain account-byte `Svm.Sdk.Storage.BoundedVec` values with fixed indexes and
sentinels. This slice does not support simultaneous vector handles, generic element layouts,
implicit growth/reallocation, pop/insert/remove/iteration, byte/string writers, or a persistent
heap collection.

The extractor's effect-retention gate now includes every Memory and TransientVec Runtime leaf.
Focused guards pin complete per-method sequences such as
`begin → push → push → set → get → finish`, preventing an ignored scalar result from erasing a
preceding VM effect during Lean-let normalization.

## Evidence

- Focused Lean extraction/emission guards validate geometry, Component ownership, full source
  effect order, shared bump allocation, and all three terminal error classes.
- `MemoryOps` Mollusk verifies all memory host calls plus Vector64 success/error/OOM behavior;
  `AccountView` independently verifies a runtime account read round-tripping through Vector64.
- Rebuilding Phoenix and PhoenixV1Profile after moving BatchRecorder to `Heap.Emit` leaves both
  assembly and ELF SHA-256 hashes byte-identical.
- Final aggregate Lean, registered-artifact, Mollusk, and Surfpool results are recorded by the
  integrating commit's verification report. Surfpool remains the only deployment gate; no
  test-validator path is introduced.

R3-021 subsequently added a second compile-time Vector64 slot through the same component and heap
contract; this original slice's slot-0 encoding and consumer digests remain stable.
