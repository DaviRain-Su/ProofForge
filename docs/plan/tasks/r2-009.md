# R2-009 — Checked fixed-account lamport mutation

## Goal

Provide the Solana AccountInfo-style direct lamport movement contract through typed static
`Svm.Sdk.Account.Handle` values, while keeping raw Loader-v3 pointers/markers out of application
source and preserving the existing generic Component boundary.

## Delivered contract

- `Handle.transferLamports destination amount` erases the two handles to compiler-proven account
  indexes. `Svm.Lamports.Call.transfer` is a narrow target-owned physical effect; no new generic
  top-level Ops/IR constructor, protocol rule, System CPI, heap object, or persistent pointer is
  introduced.
- Before either lamport store, the emitter validates distinct canonical header pointers, both
  writable flags, source owner=current program, source balance ≥ amount, and destination
  nonoverflow. A writable foreign-owned destination is valid. Amount zero follows the same gates.
  Every rejected condition returns `Custom(1)` without changing account balances or State.
- Programs using the effect select an alias-aware static Loader-v3 walk. A non-`0xff` entry must
  be an earlier index followed by seven zero bytes; it reuses the earlier saved canonical header
  and advances eight bytes. Forward/self/out-of-range/malformed aliases fail closed. A source and
  destination resolving to the same canonical header are rejected before writes.
- The reusable `Component.Call.requiresCanonicalAccountAliases` capability selects that walk;
  neither the main emitter nor program analysis names the lamport feature, so another direct
  account effect can reuse the same Loader-v3 ABI contract without a new feature-specific switch.
- Programs without the effect retain the existing strict walk. AccountView+lamport programs still
  select the variable duplicate-rejecting walk; unifying that composition remains explicit work.
