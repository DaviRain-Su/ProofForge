# L5-058 — Bounded two-maker Phoenix Limit settlement

## Goal

Compose the existing account-storage, bounded scalar-frame, and batch-recorder components into a
two-maker Phoenix Limit path without adding Phoenix-specific target operations. The source should
preflight every supported fill before mutating persistent state, replay the same bounded traversal
for settlement, charge one aggregate taker fee, and publish one coherent event packet.

## Delivered

- `placeLimitTwoMatchesFreeFunds512At` performs a fixed two-step read-only preflight over the
  opposite book. Its invocation-local scalar frame carries remaining base lots, adjusted quote,
  aggregate quote lots, fill count, validity, and the previous maker. It accepts only two distinct,
  non-self, no-TIF makers and fails closed for unsupported traversal shapes.
- A second fixed two-step traversal settles the preflighted makers in place through the existing
  `AccountStorage` map operations. No persistent tree or account region is copied into a Lean heap
  value, and no runtime descriptor or geometry enters contract state.
- Taker balances and the aggregate fee are settled once after both maker transitions. The event
  packet contains `Fill[0]`, `Fill[1]`, and `FillSummary[2]`; the summary and fee therefore describe
  the complete accepted traversal rather than either individual mutation.
- Raw Phoenix Limit dispatch accepts `matchLimit = 1` through the established one-maker path and
  `matchLimit = 2` through the new bounded path. Same-maker aggregation, resting remainder,
  still-crossing remainder, TIF, alternate self-trade behavior, soft funds, and remaining accounts
  remain fail closed until their complete transitions are covered.
- The extractor now preserves component effects in the continuation between two sequential scalar
  frames. A focused fixture proves that the second loop's account-storage mutation remains before
  frame publication instead of being erased while normalizing the first loop's continuation.
- The account-storage emitter's field-policy discriminator now uses short-lived expression scratch
  rather than an invocation-state slot. This keeps its lifetime disjoint from the batch recorder's
  pointer/length state when both components are composed in one complex traversal.
- No generic Ops, IR, CFG, Component, SVM Emit operation, or protocol-specific emitter vocabulary
  was added. Phoenix owns crossing, balance, fee, event, and packet policy; reusable components own
  storage mutation, bounded traversal state, and recording.

The composed boundary is:

```text
Phoenix two-maker policy in Examples
        │ fixed read-only preflight using scalar-frame + AccountStorage queries
        ▼
accepted aggregate totals and exact maker sequence
        │ fixed replay using AccountStorage mutations + BatchRecorder
        ▼
maker settlement → one taker/fee settlement → Fill, Fill, FillSummary
```

Persistent state remains fixed account bytes with fixed strides, one-based indexes, and the `0`
sentinel. This slice adds no persistent heap `Map`/`Vec`, dynamic pointer, runtime geometry,
detached tree, or unbounded traversal.
