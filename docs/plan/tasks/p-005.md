# p-005 SDK 组件形式化验证：三层策略 + 第一批几何证明

## 问题

合约层（Examples/*）已有 26 个 kernel 定理，但 SDK 组件层
（Svm.Sdk.Storage / Evm.Sdk / Core.Codec）一个定理都没有。
SDK 组件要不要形式化验证？答案是分三层，按「Lean 里能不能看见真实语义」划分。

## 三层策略

**第一层：纯描述符算术（现在就证，kernel 直接检查）**

SDK 里大量逻辑是纯 Nat/UInt64 算术，没有任何运行时值：
wellFormed 谓词家族、firstWord 几何、fail-closed 卫语句、capacity 上限。
这些是真正的 SDK 安全合同，kernel 直接检查：

- `scalarHeader_wf_account` / `scalarHeader_wf_width`：header 钉死同账户、1 word
- `boundedVec_wf_same_account`：count header 与 payload 槽同账户
- `boundedVec_wf_header_before_slots`：header 字在首个 payload 槽字之前
- `boundedVec_wf_count_disjoint`：**任何 payload 槽字都不可能是 count header 字**
- `rbTree_wf_parentColor_in_slot`：parentColor 字段落在 links 槽 stride 内

**第二层：效果型组件（需要抽象账户状态模型，下一步）**

read/write/RbMap find/insert 委托给 `@[irreducible]` 宿主占位
（`accDataWordAt` 等）。对 stub 的证明验证的是占位而非链上行为——这是
「证 A 编 B」陷阱的 SDK 版。正确路径：引入抽象账户字状态模型
（`AccountWords ≈ Nat → UInt64`），把原语在该模型上解释，证 SDK 代数
（read-after-write、不相交区域互不干扰、alloc/free 往返、push/pop 后
count 一致），然后信任边界声明「发射的 sBPF 由 pinned Mollusk
工程门验证实现同一原语」。这把信任边界从「kernel + 合约」扩展为
「kernel + 合约 + SDK 组合逻辑 +（工程门）原语」。

**第三层：目标指令语义（明确不做）**

sBPF/Yul 的 refinement——发射代码逐步实现模型语义。项目信任边界
（README）明确不声称；成本远超当前收益。

## 第二层进度（StorageModel.lean，已落地）

（`mFieldWord`/`mReadField`/`mWriteField`，镜像 Source.read/write 的
几何与哨兵约定）已 kernel-check：

- 读后写、越界读 0 / 写 noop、接口条件版非干涉

  的 fail-closed 代数：越界 getAt=0、越界 setAt noop、满推 noop、空弹 noop
