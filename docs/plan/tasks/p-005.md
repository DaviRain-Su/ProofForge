# p-005 SDK 组件形式化验证：三层策略 + 第一批几何证明

## 问题

合约层（Examples/*）已有 26 个 kernel 定理，但 SDK 组件层
（Svm.Sdk.Storage / Evm.Sdk / Core.Codec）一个定理都没有。
SDK 组件要不要形式化验证？答案是分三层，按「Lean 里能不能看见真实语义」划分。

## 三层策略

**第一层：纯描述符算术（现在就证，kernel 直接检查）**

SDK 里大量逻辑是纯 Nat/UInt64 算术，没有任何运行时值：
wellFormed 谓词家族、firstWord 几何、fail-closed 卫语句、capacity 上限。
这些是真正的 SDK 安全合同，kernel 直接检查：

- `scalarHeader_wf_account` / `scalarHeader_wf_width`：header 钉死同账户、1 word
- `boundedVec_wf_same_account`：count header 与 payload 槽同账户
- `boundedVec_wf_header_before_slots`：header 字在首个 payload 槽字之前
- `boundedVec_wf_count_disjoint`：**任何 payload 槽字都不可能是 count header 字**
- `rbTree_wf_parentColor_in_slot`：parentColor 字段落在 links 槽 stride 内

**第二层：效果型组件（需要抽象账户状态模型，下一步）**

read/write/RbMap find/insert 委托给 `@[irreducible]` 宿主占位
（`accDataWordAt` 等）。对 stub 的证明验证的是占位而非链上行为——这是
「证 A 编 B」陷阱的 SDK 版。正确路径：引入抽象账户字状态模型
（`AccountWords ≈ Nat → UInt64`），把原语在该模型上解释，证 SDK 代数
（read-after-write、不相交区域互不干扰、alloc/free 往返、push/pop 后
count 一致），然后信任边界声明「发射的 sBPF 由 pinned Mollusk
工程门验证实现同一原语」。这把信任边界从「kernel + 合约」扩展为
「kernel + 合约 + SDK 组合逻辑 +（工程门）原语」。

**第三层：目标指令语义（明确不做）**

sBPF/Yul 的 refinement——发射代码逐步实现模型语义。项目信任边界
（README）明确不声称；成本远超当前收益。

## 第二层进度（StorageModel.lean，已落地）

抽象账户字状态模型 `AccountWords := Nat → UInt64` + 字段级原语
（`mFieldWord`/`mReadField`/`mWriteField`，镜像 Source.read/write 的
几何与哨兵约定）已 kernel-check：

- 读后写、越界读 0 / 写 noop、接口条件版非干涉
- 标量 header 的访问词 = firstWord（由 scalarHeaderWellFormed 推出）
- 线性分离引理 `add_mul_inj`（不相交字段推理的几何基础）
- BoundedVec 模型操作（mBvSize/GetAt/SetAt/Push/Pop，卫语句与 SDK 逐字对应）
  的 fail-closed 代数：越界 getAt=0、越界 setAt noop、满推 noop、空弹 noop

下一片：wf 前置下的 push/pop count 一致性与 push-then-getAt
（需要 count/slots 非干涉，由 header_before_slots + add_mul_inj 推导）、

### wf 桥接的已知坑（下一片的实施注意）

`BoundedVec.wellFormed`/`scalarHeaderWellFormed`/`Field.mutableOneBasedWord`
的 Bool-and 链在 `simp only [..., Bool.and_eq_true]` 后是**左嵌套 And**，
且逐叶投影路径（`h.1.1.1.2` 型）在不同上下文下不可靠（simp 的重排会让
位置漂移）。下一片应先写一个小型辅助 tactic（或把 wellFormed 定义改写成
结构化 And 的引理包），统一叶提取，再证桥接定理：
`boundedVec_wf_indexBase`（slots one-based）、`boundedVec_wf_capacity`
、`mFieldWord_bv_slots`、`mFieldWord_bv_count`、
`mFieldWord_bv_count_ne_slots`（带无回绕前置 hwrap，由
Field.wellFormed 的 maxDataWord 界在使用点给出）。
另外 `IndexBase` 无 LawfulBEq——`(b == zero) = true → b = zero` 需要
辅助引理 `IndexBase.beq_zero_eq`（cases + decide，已验证可行）。


## 合并后的验证表面清单（origin/main 0fc9f9b SDK parity 冲刺，2026-08-28）

远程新增的 SDK facade 是第一/二层验证的新目标，按纯度分类：

**第一层（纯守语句/谓词，kernel 可直接证）**
- `Evm.Sdk.Pausable`（48 行）：canonical flag 语义——unknown flag 既非 running
  也非 paused（fail-closed）、pause/unpause 转换对合、`isRunning (paused) = false`。
  全部是 UInt8 纯谓词；且抽取器已支持 UInt8/16/32 scalar helper（r5-004），
  这些性质直接是链上相关性质。
- `Evm.Sdk` bounded static role sets：纯成员谓词。
- `Svm.Sdk.Token`（209 行）/`Account`/`Pda`/`System`/`AssociatedToken`/`Memo`
  的卫语句与几何部分：凡走 BoundedVec/Region 描述符的，直接落在已有
  StorageModel 字段代数 + wf 桥的覆盖范围。

**第二层（模型层已就位，待推广）**
- `StorageModel.lean` 的 AccountWords 模型 + 字段级代数 +
  `mBvPush_twoWrites`（count/slots 双写一致）——新 facade 里的 Token balances、
  Queue、Transient 等容器复用同一批原语引理。

**优先级**：Pausable fail-closed 语义（最小、最纯、直接对应 OZ 语义）
→ Token facade 守语句 → Transient/Account → RbMap 代数。
