# R5-007 — EVM checked credit and alias-safe transfer

## Goal

Complete the balance-movement half of the reusable fungible ledger without adding ERC-20 recipes to
Ops or Emit. Close two real semantic gaps: additive credit must reject UInt256 wraparound, and a
same-address transfer must not debit and credit the same hashed key through two writes.

## Delivered contract

- `Evm.Sdk.Fungible.Balances` adds `canCredit`/`credit` and `canTransfer`/`transfer` beside the R5-006
  debit surface. `canCredit` requires `next ≥ current`; `transfer` is a no-op for equal addresses
  after the source debit gate and otherwise composes the existing debit and credit writes.
- Token mint now adds to the recipient balance and checks `value ≤ cap - supply`, preventing both
  balance and supply wrap. Direct and delegated same-address transfers preserve balance; the
  delegated path still spends allowance and applications still own event ordering.
- Vault's share ledger is the second checked additive-credit consumer. Its repeated credits add,
  while `max_uint` over an existing balance fails atomically.
- Authorization, pause and zero-address gates, cap choice, allowance storage/policy, event topics,
  and typed State writes remain application-owned and visible.

There is no new Runtime leaf, Op/IR/Component/Emit case, selector, event/error recipe, runtime layout
object, heap allocation, or cross-target storage abstraction.

## Resource and fail-closed boundary

All operations are O(1) over one compile-time `AddressMap256` namespace. Mutation methods retain
explicit preconditions, so applications choose failure and event ordering. Destination overflow and
mint cap/supply wrap fail before a write. Equal-address movement emits no balance write; delegated
movement may still update its separate allowance namespace. Reusable allowance policy, ERC-721, and
bounded ERC-1155 remain unavailable.
