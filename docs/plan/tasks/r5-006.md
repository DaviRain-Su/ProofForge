# R5-006 — EVM fungible debit ledger foundation

## Goal

Start the reusable asset layer with one honest persistent balance component rather than adding
ERC-20 recipes to Ops or Emit. The first slice owns balance lookup, debit eligibility, checked
debit composition, and the existing typed insufficient-balance terminal.

## Delivered contract

- `Evm.Sdk.Fungible.Balances` is an explicit compile-time
  `Storage.AddressMap256` handle. `balanceOf`, `canDebit`, `debit`, and `insufficient` erase through
  `pf_inline` to the existing hashed-map, UInt256, and native-error components.
- Token uses the component for balance reads and direct/delegated burns. Credits independently uses
  it for credit reads and claims, satisfying the two-consumer gate with different application
  policy.
- Authorization, pause ordering, zero-address checks, supply/cap accounting, allowance spending,
  events, and typed State writes remain application-owned and visible.

There is no new Runtime leaf, Op/IR/Component/Emit case, runtime layout object, slot allocator,
selector, event topic, error selector, heap allocation, or cross-target storage abstraction.

## Resource and fail-closed boundary

The handle selects one persistent EVM hashed namespace at compile time. Every operation is O(1).
`debit` has the explicit precondition `canDebit`; consumers retain control of failure ordering and
use `insufficient` on the false branch. Credit/mint, same-address-safe transfer, allowance policy,
ERC-721, and bounded ERC-1155 are deliberately not claimed by this first asset slice.
