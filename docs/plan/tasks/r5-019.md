# R5-019 — Persistent bounded EVM enumerable UInt64 map

Date: 2026-08-30
Status: done

## Goal

Provide the bounded persistent equivalent of OpenZeppelin `EnumerableMap` for `UInt64 → UInt64`
by composing the existing enumerable-set index with an independent value namespace, without adding
a map opcode, runtime slot allocator, pointer, unbounded key array, or application-specific
Extract/IR/Emit case.

## Delivered contract

- `Evm.Sdk.StorageEnumerableMap.Descriptor capacity` contains an existing
  `StorageEnumerableSet.Descriptor capacity` for fixed key vector/count/position+1 indexing and a
  distinct `Storage.U64Map` for values. Descriptor validation requires exact static geometry,
  positive codec-representable capacity, and disjoint position/value namespace bases.
- The position map is the sole presence authority. Position zero means absent, so both key zero
  and value zero remain valid data. Malformed count, a nonzero position outside the active prefix,
  or a position/backing-key mismatch fails before every mutation.
- Insert, update, lookup, indexed key/value access, and swap-remove are O(1). Insert writes one key,
  one position, one value, and count. Update touches only the value namespace. Removal clears both
  removed-key namespaces; middle removal additionally moves the last key and repairs only that
  moved key's position.
- `EvmConfigMap` is an owner-gated capacity-4 consumer with shared `CapExceeded()` growth policy
  and strict malformed lookup. `EvmScoreMap` is an independent permissionless capacity-3 consumer
  with application-owned `full()` and non-reverting malformed view fallbacks.

## Resource and ownership boundary

The SDK owns reusable descriptor geometry and pure fail-closed decisions. Consumers retain literal
fixed-vector/count updates and explicit map puts, so target effects remain visible to extraction.
Middle removal has three hashed writes plus one vector write; last/only removal has two hashed
writes and no vector write. No operation scans capacity, and no descriptor survives into runtime
storage.

This slice adds no Runtime leaf, top-level Ops/IR constructor, Component variant, or Emit recipe.
It reuses ordinary static `sload`/`sstore`, fixed-vector extraction, and two compile-time hashed-map
namespaces. Authorization, error, and absent-view policy remain in `Examples`.

## Explicit boundary

V1 stores only UInt64 keys and values with compile-time positive capacity. Address/Bytes32/UInt256
keys or values, ordered iteration, bulk clear, dynamic capacity, packed values, runtime-selected
namespaces, and unbounded Solidity arrays remain unavailable. Richer shapes require separately
qualified bounded physical contracts, not a runtime allocator or emitter special case.
