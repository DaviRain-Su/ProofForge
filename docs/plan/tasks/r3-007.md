# R3-007 — SVM Associated Token and Memo SDK facades

## Goal

Give the remaining fixed ATA and Memo Runtime compositions honest source-level SDK owners without
copying their account metas, instruction bytes, or validation into applications or a new emitter
recipe.

## Delivered contract

- `Svm.Sdk.AssociatedToken.createIdempotent` names the existing modern ATA
  `CreateIdempotent` shape: payer, associated account, wallet, mint, System program, and an
  explicitly supplied Token program. It does not substitute classic Token for account 5, so the
  transaction can select the Token program appropriate for its mint.
- `Svm.Sdk.Memo.writeOk` honestly names the current closed two-byte memo. The name does not imply a
  dynamic String or byte-buffer API.
- Ata and Memo applications plus their focused tests consume SDK names; direct Runtime wrappers
  remain the target boundary, not an alternative application API.

Both functions are `pf_inline` delegates. No account table, instruction buffer, pointer, heap
collection, persistent allocation, Ops/IR/Component/Extract/Emit case, or program-specific
extractor whitelist is added.

## Fail-closed boundary

Associated Token ordinary Create, RecoverNested, alternate geometry, address derivation helpers,
and canonical program-id policy remain future contracts. Memo data other than the fixed `"ok"`
literal requires a bounded byte codec/Runtime surface and remains unavailable. The facade does not
hide either limitation behind a generic-looking parameter.

## Evidence

- Focused SDK, Ata, and Memo gates pass; extracted IR retains canonical digests
  `574dc90c21ca9723` and `26a3540da902ccb5`.
- All six Ata/Memo assembly, ELF, and IDL artifacts are byte-identical to the pre-facade baseline.
- Aggregate Lean, ownership, whitespace, and Markdown-link gates pass. Mollusk and Surfpool are not
  repeated because both machine programs are byte-identical; Surfpool remains the only deployment
  qualification environment.
