# CI-001 — Run shared Lean guards once beside target lanes

## Problem

The SVM and EVM jobs were independent, but both ran the same `lake build` and complete
`lake build Tests`. The aggregate includes the large Phoenix, Phoenix-v1, and build-spec modules,
so the most expensive 356-job Lean gate was compiled twice on every CI run. The duplicated work
made the EVM lane wait on SVM-heavy Lean modules before it could report target feedback.

## Delivered contract

- `Lean` owns the shared ownership/artifact/no-placeholder checks plus `lake build` and the full
  `lake build Tests` aggregate.
- `SVM` owns all registered sBPF builds, locked Mollusk, and the three Surfpool Loader-v3 deploy
  gates. `EVM` owns all registered solc builds and the registered Anvil aggregate. Each target lane
  first builds the `Examples` source library required by the CLI's dynamic module imports, but does
  not repeat the test aggregate.
- Each target lane validates the actual clean build directory against its registry immediately
  after `pf build`, before runtime fixtures can add generated artifacts. The synthetic manifest
  self-test remains in the Lean lane but no longer substitutes for checking produced artifacts.
- Surfpool readiness requires both `getHealth = ok` and a valid `getVersion` response before the
  deployment client starts. Cleanup gives Surfpool a bounded SIGTERM grace period and then uses
  SIGKILL, so a failed smoke cannot hang the lane indefinitely.
- The three jobs have no dependency edges and start independently. The existing required `test`
  identity waits for all three and fails unless every result is `success`, including when another
  lane has already failed.

This does not weaken coverage or split target-sensitive tests by filename. Shared and cross-target
Lean guards still run together exactly once; physical target gates remain in their owning lanes.

## Evidence

- Current integrated gates pass: ownership/no-placeholder checks, 14-case manifest self-test,
  406-job `lake build Tests`, clean manifests for 67 SVM and 40 EVM programs, locked Mollusk
  421/421, and Anvil 40/40.
- Surfpool 1.5.0 passed Phoenix, PhoenixV1Profile, and RawEntry sequentially under the stricter RPC
  readiness/cleanup contract. The current VersionedLedger smoke also passed with 15 Loader-v3
  writes and exact 14,704-byte ELF verification.
