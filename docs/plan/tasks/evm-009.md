# EVM-009 — Bound address packing behind a runtime Yul helper

## Goal

Restore the full EVM CI gate on solc 0.8.34 without disabling optimization or changing contract
semantics. The generated Token Yul failed in `transferFrom(address,address,uint256)` because each
address write expanded twenty byte stores directly into multiple cases of the same CFG dispatcher.

## Delivered

- Added one generated runtime function, `pf_store_addr20(off, w0, w1, w2)`, that owns the existing
  little-endian three-limb to ABI-address byte shuffle.
- Replaced every inline address-memory expansion with a call to that function. ABI words, external
  call calldata, return values, event topics, custom errors, and address comparisons retain the
  same byte layout.
- Kept strict Yul optimization enabled. The unoptimized 34,883-byte workaround was rejected because
  it exceeded the EIP-170 24,576-byte deployment limit; the fixed optimized Token is 15,202 bytes.
- Added an emitter shape guard so Token Yul must contain and call the shared helper and must not
  regress to a directly expanded `mstore8(12, ...)` sequence.
- Added no EVM Op, IR node, CFG case, contract special case, compiler flag, or optimizer exception.
  The change is entirely within the emitter's reusable address-encoding boundary.

## Verification

- `lake build Tests` completed all 214 jobs.
- `lake exe pf -- build --target evm --out build/evm` built all 14 registered EVM programs with
  solc 0.8.34; Token produced 15,202 bytes of deployment bytecode.
- `runtime-tests/evm/anvil.sh` passed 14/14, including Token transfer, allowance, permit, logs,
  zero-address rejection, burn, metadata, and Vault external-call address encoding.
- Recent remote SVM steps were inspected separately: Lean, all 51 SVM builds, Mollusk, and all three
  Surfpool deployment gates were green. The reported CI failure was the later EVM build step, so no
  SVM behavior or deployment gate was weakened.
