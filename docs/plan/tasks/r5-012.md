# R5-012 — Harden closed EVM call results and preserve explicit source returns

## Goal

Bring the default closed token-call contract up to the SafeERC20 safety boundary without exposing
arbitrary calls or making application authors reproduce returndata/code-existence checks. At the
same time, keep an explicit source return distinct from the numeric carrier used to sequence a
preceding storage, event, or call effect.

## Delivered contract

- `Evm.CallResult` remains the only closed CALL/STATICCALL result interpreter. ERC-20 mutations now
  require CALL success and either exactly one 32-byte canonical word `1`, or empty returndata from a
  target that still has runtime code after the call. It rejects `0`, noncanonical words such as `2`,
  all other lengths, and empty success from an EOA/no-code address.
- Success-only contract calls do not copy returndata. A nonempty result is ignored; an empty result
  is accepted only when the target still has runtime code. Exact-word STATICCALL remains exactly
  32 bytes. Every policy copies at most 32 bytes.
- This is deliberately stricter than OpenZeppelin SafeERC20's current `returndata.length >= 32`
  compatibility branch: ProofForge accepts exactly 32 bytes for the typed Boolean result. CALL
  failures still use empty `revert(0, 0)`; arbitrary revert-data bubbling remains a separate bounded
  Runtime task and is not claimed here.
- `Evm.Sdk.Effect.thenTrue` is a reusable source combinator for sequencing a `UInt64` effect carrier
  into a canonical Boolean ABI result. Token's `approve`/`transfer`/`transferFrom` expose `bool`
  without application-level `||| 1` magic or returning the transfer amount as the success word.
- Extraction now retains the explicit second component of `.ok (state, result)`. CFG emission
  distinguishes the three legacy statement-shaped scalar map queries (whose value is carried in
  `pf_last`) from mutation effects; a later explicit return wins over event/write/call carriers.
  No top-level Ops/IR constructor or component-specific main-emitter recipe was added.
- EIP-2612 `permit` uses contract-success rather than ERC-20 Boolean-return policy because the
  standard permit function has no Boolean result.

## Evidence

- `Tests.EvmCallResultSpec` pins byte-exact result-policy emission, the no-code/empty guards, the
  explicit-result-after-effect CFG invariant, and live Token extraction to Boolean metadata plus a
  canonical success expression.
- `runtime-tests/evm/anvil_vault.sh` covers EOA/no-code empty success rejection, false-word and
  noncanonical-word-2 rejection with rollback, code-backed no-return acceptance, and the internal
  ProofForge Token permit/`transferFrom(..., 12)` path returning canonical `1`.
- Canonical source digests changed where explicit source results now become authoritative:
  EvmBounded `5258e5a9356a2a9e`, Collectible `d520f4e720c2fb7b`, Badge
  `ea3aeabda40d9ffa`, TipJar `7928fa1163c52a21`, Vault `d880e1a77eca6762`, Token
  `269a68fd54506509`, and Capped `bd609aceeaafd713`. All registered EVM source digests were checked.
- The compatibility Token fixture now declares the three standard mutation results as Bool and has
  digest `59f8696f9b0e06db`. With solc 0.8.34, Token deployment bytecode is 21,610 bytes and Vault is
  9,356 bytes.

## Remaining boundary

Bounded revert-data capture/bubbling, generic typed calldata/results, CREATE/CREATE2, delegatecall,
proxy semantics, and unbounded returndata remain fail closed. Code presence is used only as one
post-call condition for the two explicit empty-result policies; it is not an EOA/authentication
predicate and does not guarantee that a future call will succeed.
