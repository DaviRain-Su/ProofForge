# R2-001 — SVM-RT-1 bounded remaining-account view

## Goal

Give source programs a reusable, target-owned way to read one of a compile-time bounded window of
remaining accounts by a runtime-safe index. The view must validate the index against both the
compile-time capacity and the runtime available account count, reuse the existing account-header
walk and metadata/data access patterns, and fail atomically (`Custom(1)`) on out-of-window access.
Persistent state remains fixed account bytes: the view is read-only, and no pointer, heap
`Array`/`Map`, invocation pointer, or runtime geometry may be persisted. No application/Phoenix
policy and no container-shaped Core Op.

## Delivered contract

`Svm.AccountView` is a new target-owned component query vocabulary, bridged through the existing
`Svm.Component.Query` seam (no new top-level SVM Ops/IR/emitter case beyond the component bridge):

- `View { base, capacity }` — compile-time window over physical accounts
  `[base, base + capacity)`; physical account 0 stays reserved for authenticated state.
  `wellFormed` requires `base ≥ 1`, `capacity > 0`, and `base + capacity ≤ 64`
  (`maxTxAccountLocks`). Presence of individual accounts is deliberately **not** static: it is a
  runtime property checked against `NUM_ACCOUNTS` at every access.
- `Query.header` (lamports / dataLen / isSigner / isWritable / key word 0..3),
  `Query.ownerIsSelf`, and `Query.dataWord` — each with one runtime zero-based `index` operand.
- `Svm.Sdk.Account.View` is the current `pf_inline` facade: a contract names its window once
  (`Account.View.bounded base capacity`) and reads through `peekData` / `peekKey` / `peekSigner` /
  `peekWritable` / `peekDataLen` / `peekLamports` / `ownedBySelf`. The handle erases completely at
  extraction; data/key word selectors are compile-time `Nat` values, and the extracted IR contains
  only the component query plus its runtime account index. R3-002 moved the source API into the
  unified SDK owner without changing this R2 target contract.
- `Svm.Runtime` exposes the matching irreducible host stubs (`viewLamports`, `viewDataLen`,
  `viewIsSigner`, `viewIsWritable`, `viewKeyWord`, `viewOwnerIsSelf`, `viewDataWord`).

### Lowering and resource bounds

At every access the emitted target code, in order:

1. loads the runtime index and checks `index < capacity` (compile-time bound);
2. checks `base + index < NUM_ACCOUNTS` (available accounts);
3. walks the real account headers in place — 88-byte header layout, `data_len`-plus-`MAX_
   PERMITTED_DATA_INCREASE` alignment skip — verifying the `0xff` (`NON_DUP_MARKER`) tag byte of
   every traversed account, and reads the selected header field or `data_len`-checked data word.

Any violation exits `Custom(1)` atomically before selected field/data bytes are read or state is
stored. The walk keeps only the cursor and one counter in registers; there is no scratch, no
allocation, no copied node, and no pointer outside the invocation.

### Account-view walk contract (ABI pointer fix)

Variable remaining accounts move the real instruction data and program id after the *actual*
final account, so the static unrolled prelude walk cannot locate them. When a program uses an
account view (`IR.usesAccountView`), the entry, dispatch, and every handler prelude switch to a
bounded account-view walk that traverses the runtime `NUM_ACCOUNTS`, hard-bounded by
`maxTxAccountLocks` (counts above the limit fail closed), stores the required static prefix
headers `0..n-1` for CPI/flag checks, and stores the instruction-data pointer of the actual final
account in the trailing header cell. All downstream consumers (instruction-data length, program
id, walk-ABI arguments at `r7`, state authentication) read that same cell and are unchanged.
Programs without an account view keep the byte-stable unrolled prefix walk.

### Emitter okState correction (pre-existing, exposed by the fixture)

`emitOkState`'s fallback previously assumed the checked-add accumulator slot held the next state
value whenever the method had checked arithmetic, silently dropping the actual value tree when it
referenced a `letLocal`-defined local or a component result (storing a stale sum instead). The
shortcut is now restricted to pure static arithmetic trees over arguments/fields/literals; any
other value is loaded explicitly. Programs whose okState values never hit that path keep their
previous bytes.

## Consumers and evidence

- `Examples.Svm.AccountView`: one compile-time `window` handle over physical accounts 1..4 with
  `peek*` readers and an `absorb` mutating entry that composes the view read into a checked
  state update.
- `Tests.AccountViewSpec`: focused extraction/emission guards — the view lowers to the
  `accountView` component query, `usesAccountView`/walk layout, static prefix `base + 1`, the
  runtime account-count walk with the `maxTxAccountLocks` hard bound, index/capacity checks, and
  the fail-closed facade boundaries.
- `runtime-tests/solana/tests/account_view.rs` (Mollusk, 11 cases): selected data/key/lamports/
  data-len words follow the runtime index; signer/writable/owner flags follow the metas;
  capacity OOB and available-count OOB fail atomically; duplicate keys fail closed on the
  `NON_DUP_MARKER` walk discipline; short data fails before the data pointer is formed; `absorb`
  commits the selected word plus delta; `absorb` with an out-of-window index holds state
  byte-identically; `initialize` writes marker and value over the full window.
- Focused regression: all 54 registered SVM programs still emit, and the counter/window/pair/
  flag/choice/seat/tree/book/trio/ticket_line/job_queue Mollusk suites pass unchanged.

## Fail-closed boundary

- The view is read-only; there is no write path and no duplicated window state.
- Duplicate account keys inside the window (Loader-v3 one-byte `NON_DUP_MARKER` entries) are
  rejected atomically by the tag discipline, like every malformed account header; resolving
  duplicate headers remains future work and is consistent with the existing static walk.
- Account counts above the transaction-account-lock limit fail closed.
- Runtime-selected geometry, persistent pointers, heap containers, and application policy are
  not expressible through this component.
