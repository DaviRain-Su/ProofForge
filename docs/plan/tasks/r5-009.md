# R5-009 — EVM reusable reentrancy policy

## Goal

Publish an OpenZeppelin-shaped reentrancy guard at the SDK policy layer by composing the existing
schema-resolved ordered static UInt64 store and bounded ETH CALL. A lock must be visible before a
hostile callback, restored after a successful call, and rolled back atomically when the call fails,
without adding a Reentrancy-specific Runtime operation or emitter recipe.

## Delivered contract

- `Evm.Sdk.Reentrancy` owns canonical nonzero sentinels (`notEntered = 1`, `entered = 2`), a
  fail-closed `canEnter` predicate, and explicit ordered `enter` / `leave` operations over one
  `Storage.Static.Handle UInt64`.
- The application keeps the status field in ordinary typed State, declares its compile-time static
  handle, chooses the external call, and owns the typed rejection terminal. Every status other than
  `notEntered` is rejected.
- `GuardedPayout` is an application-owned consumer. `EvmOrderedStorage` is a second consumer and
  retains its canonical digest after replacing literal lock policy with the SDK names.
- The lock API intentionally does not use a higher-order wrapper: lexical `enter → CALL → leave`
  remains visible to extraction and review, while EVM transaction semantics own failed-call
  rollback.

## Resource and ownership boundary

The policy consumes one compiler-static 8-byte field and O(1) effects. The handle is resolved
against the extracted State schema; no raw slot, runtime allocator, hidden final write, heap value,
arbitrary call, selector, or returndata buffer is exposed. There is no new Ops/IR/Component/Emit
case. Generic declared custom errors remain a separate language-surface gap, so each application
owns its typed `Except` variant instead of adding a closed reentrancy error to the Runtime.

## Evidence

- The aggregate `lake build Tests` gate passes 312 jobs.
- Focused Lean guards prove both consumers extract exact `store 2 → ETH CALL → store 1` order,
  contain their fail-closed typed terminal, and do not lower the lock as final State writeback.
- `GuardedPayout` builds through solc 0.8.34 and executes on Anvil.
- A real Solidity callback fixture observes status `2`, attempts the same guarded payout, catches
  the nested revert, and proves the outer call restores status `1`. A normal call succeeds, and an
  unfunded failed CALL proves transaction rollback preserves status `1`.
- Digests are `359f6025f96aa432` (`GuardedPayout`) and unchanged `c37f9c0a33352f4`
  (`EvmOrderedStorage`).
